# Unified Enterprise Service Management

## Overview

A single Enterprise Service Management platform gives service teams one governed way to receive and manage requests while preserving each department as a configurable workspace. It replaces department-specific application boundaries with shared requests, people, settings, navigation, and permission policies.

## Architecture direction

The platform follows clean architecture and remains self-hostable. Domain and application logic depend on provider interfaces rather than generated storage services, database SDKs, or automation vendors. The current in-memory implementation is the first supported persistence provider; PostgreSQL is the recommended first durable provider, with SQL Server, MySQL, Dataverse, SharePoint, and REST backends available through replaceable adapters. A production deployment can run on a VM with the React client, a stateless API, a durable background worker, protected file storage, a relational database, and OpenID Connect authentication. Entra ID and Microsoft Graph are preferred enterprise identity and directory adapters, while Azure Functions, Power Automate, Dataverse, SharePoint, and Azure Storage remain optional integrations rather than platform requirements.

## Initial workspaces

Information Technology, Corporate Communications, Facility Management, Support Services, Rawabi Travel & Tourism, Government Affairs, and RVOS Support.

## Roles

- Requesters submit and follow requests within authorized workspaces.
- Service agents fulfill, assign, transition, and resolve requests according to explicit grants.
- Workspace administrators configure workspace membership, modules, and overrides without inheriting global administration.
- Platform administrators govern global definitions and explicitly authorized cross-workspace operations.
- Auditors receive read-only access where assigned.

## Foundation scope

The platform uses one shared Request entity. Every workspace-owned record carries WorkspaceId. Workspace records hold editable identity, ownership, locale, numbering, portal, and audit configuration. WorkspaceMembership grants workspace visibility and administrative context; ServiceMembership separately grants Agent, Service Manager, Service Administrator, Approver, or Auditor access to one service. Neither boundary implicitly grants the other.

The persistent application shell carries active workspace context across all configured module routes. Module and WorkspaceModule records drive labels, icons, sorting, visibility, permission requirements, and workspace overrides for desktop and mobile navigation. Disabled or unauthorized modules are absent from navigation and rejected on direct access; workspace changes rebuild the module set before scoped content renders.

Request details retain exactly five tabs: Activity, Details, Work, Resolution, and History. Core modules are available across workspaces, while specialist modules are selectively configured without adding operational feature screens in this foundation.

Global Administration and Workspace Administration are separate protected scopes. Global roles govern platform-wide workspaces, people, roles, sites, calendars, integrations, retention, audit, health, and module definitions; workspace administrators manage only explicitly assigned workspaces. Administration context is adaptive: one administered workspace renders as a static identity with no redundant picker, while multiple administered workspaces expose a switcher containing only active Owner or Administrator memberships. Settings routes redirect safely to an administered workspace when the requested workspace is outside that scope. Settings resolve through global default, workspace override, service or catalog item override, and request-calculated value, with effective source visibility, reset-to-inherited behavior, and configuration audit events for every change.

Authorization resolves from the active Power Apps identity through global role, effective workspace membership, service membership, record scope, field grants, lifecycle grants, and environment restrictions. Workspace roles no longer imply operational access to every service: agent and manager queues are constrained to explicit active service memberships, while requester ownership remains a separate record boundary. Request queries are scoped at the data-service boundary rather than fetching unrestricted records; direct routes, global search, exports, notifications, attachments, and reports use the same policy vocabulary.

All operational work uses the single shared Request entity, with immutable workspace and request-number identity. Workspace/year sequences issue permanent numbers from each workspace's configured prefix and format, while all request activities, attachments, tasks, checklists, approvals, relationships, reminders, resolutions, worklogs, and history retain both RequestId and WorkspaceId. No department-specific ticket or request tables are used.

The Requests module presents a permission-aware, workspace-scoped queue and shared Request records at `/w/:workspaceCode/requests/:requestId`. Each detail view keeps exactly five tabs and loads related Activity, Details, Work, Resolution, and immutable RequestHistory from shared entities. Its information rail shows the SLA-calculated due time, editable request tags, managed linked requests, and earlier requests from the same requester. Public replies, internal notes, relationship changes, tag changes, and resolution changes persist through the same engine and record actor, timestamp, source, reason, field, old value, and new value.

The shared request engine enforces permanent workspace identity, guarded creation and numbering, workspace-scoped reads, permission-aware updates and lifecycle actions, required task and approval completion, resolution capture, and cross-workspace orchestration blocking. The same services and entities serve every workspace; this phase does not introduce department-specific behavior or dynamic form features.

Request-detail composition is declarative but deliberately constrained. Active ViewDefinition records select the Requester or Agent surface and version; ordered ViewSectionDefinition and ViewActionDefinition records can compose only registered request sections and handlers. Unknown renderer or action keys, inactive records, and unsupported permission declarations are not executed, and the runtime falls back to a safe built-in composition when configuration is absent or invalid.

The Services Marketplace at `/` is the requester homepage and primary landing experience for every employee. It keeps a large search-led hero and an optional Favorite Services section above a compact tabbed discovery area for Popular, Recently Used, Recommended, search results, and Business areas. Favorites contain only services explicitly saved by the employee, remain synchronized with the discovery star controls, exclude unavailable services, and stay hidden when empty—there is no popularity-based fallback. The hero pairs search with a permission-aware Action Center that hides empty categories and combines requester replies, approvals, open request tasks, today’s remaining Outlook events, and incomplete Planner or Loop tasks that are overdue or due within 48 hours. Microsoft 365 actions are loaded at runtime for the signed-in user and fail independently without blocking service discovery. Business areas provide simple filters without exposing workspace ownership; My Requests remains compact below discovery. A single minimal requester navigation links Home, Services, My Requests, My Approvals, Knowledge, and Profile; selecting a service still transfers into its owning workspace where audience, identity, form-version, and request-create policy are rechecked before submission. Users with an active Agent, Service Manager, or Service Administrator service membership—or an existing workspace/global administration grant—receive a loading-safe Open Operations action that enters the original authorized workspace operations interface; requester-only users never see it, and operations retains a clear return to the marketplace.

The Approval Engine uses reusable ApprovalDefinition, ApprovalStage, and ApprovalRule configuration rather than catalog- or request-specific code. It supports single, multiple, any, and all approver policies; sequential and parallel stages; manager, person, role, and group resolution; delegation; expiration; and escalation. RequestApproval stores runtime assignments, ApprovalDecision stores immutable outcomes, and every activation, delegation, decision, expiration, escalation, and completion action is mirrored into RequestHistory. Approvers act from the workspace queue at `/w/:workspaceCode/approvals` or directly within the request Work tab, and the same target vocabulary is available to catalog items, requests, changes, and future generic modules.

The workspace Automation Engine provides generic trigger, condition, and action configuration without department-specific code. Rules support request, approval, target, comment, assignment, and scheduled events; ordered conditions and actions; cooldown, maximum execution, and chain-depth limits; and immutable execution logs for succeeded, skipped, blocked, and failed outcomes. Workspace administrators manage only rules in the active workspace, while safety defaults prevent recursive automation loops.

The requester portal at `/w/:workspaceCode/portal` provides Requester Home, My Requests, Service Catalog, Knowledge, My Approvals, and My Assets. Request queries apply workspace and requester/requested-for ownership filters before records render; direct request routes repeat the same boundary. Request detail provides requester-safe approval and fulfillment progress, terminal-state guidance, source-specific portal or email intake context, requested-for clarity, authorized linked and previous requests, and attachment validation with scan status and time-limited deletion of the requester’s own uploads. Requesters can create and follow requests, post only public replies, upload attachments, confirm a resolution, and reopen eligible recently resolved requests. Internal notes, service queues, private operational activity, administration, and other users' requests are excluded from requester routes and data queries.

The workspace-scoped Knowledge Base stores categories, articles, immutable versions, and member feedback in shared entities. Agents and knowledge publishers can create drafts, submit reviewed versions, publish requester or agent audiences, and inspect version history at `/w/:workspaceCode/knowledge`. The requester portal exposes only Published articles intended for Requesters or All Members, with search, category filtering, and helpfulness feedback.

The Reporting workspace at `/w/:workspaceCode/reports` derives request volume, open and closed demand, aging, approval performance, service-target performance, and workload directly from permission-scoped operational records. Metadata-aware request, typed-answer, approval, SLA, and workflow projections normalize multi-select values while retaining the historical field label, type, and version. The Field Catalog at `/w/:workspaceCode/reports/fields` exposes governed eligibility, sensitivity, dependencies, and usage; Report Builder discovers newly published non-sensitive reportable fields automatically and supports filtering, grouping, sorting, saved reports, dashboards, and authorized request drill-through without source-code changes.
Service owners, backup owners, report authors, auditors, and workspace administrators can open the service-level health dashboard at `/w/:workspaceCode/reports/service-health`. It derives volume, backlog, average aging, SLA compliance and breaches, approval delays, overdue tasks, rejection exposure, and reopens from the existing permission-scoped request, approval, task, target, and status-history records. Every metric supports request-level drill-through into the universal request view, while service governance limits which services each owner can inspect.
The workspace-scoped Contracts module at `/w/:workspaceCode/contracts` gives authorized workspace administrators a supplier agreement register with create and edit forms, guarded lifecycle actions, renewal exposure, responsible ownership, linked obligation creation and completion, and an immutable activity timeline. Live normalized commercial-term and compliance-detail records capture counterparty legal identity, business and contract ownership, payment and billing terms, tax treatment, renewal and termination notice controls, decision dates, governing law, jurisdiction, confidentiality, data protection, insurance and expiry, liability caps, procurement and cost-center references, purchase orders, signature status and date, and document links. Validated operational forms create or update these records, surface renewal alerts and key controls in the contract view, and retain changes in contract activity. Vendor, Contract, ContractCommercialTerm, ContractComplianceDetail, ContractObligation, ContractDocument, and ContractActivity records retain WorkspaceId so direct access and operational data remain isolated to the active workspace. Durable document upload and scheduled renewal delivery remain explicit production integration blockers.

Catalog administration at `/w/:workspaceCode/settings/catalog` turns the existing catalog entities into an operational publishing workflow. Workspace administrators can create and edit items, search and filter the register, inspect audience, default-form, and service readiness, and move items between Draft, Published, and Retired states. Publication is blocked until the item has an active eligible audience, an active default form assignment, and an active requester-eligible service.

The Service Builder at `/w/:workspaceCode/settings/service-builder` now provides a complete three-panel no-code authoring surface: a searchable field library and sections panel, a shared-renderer canvas, and a selected-field properties panel. Administrators can create drafts from published versions, drag or keyboard-reorder fields, autosave properties, undo or redo ordering, clone fields and versions, archive drafts, configure defaults, help, custom errors, lookup and attachment settings, validations, conditional rules, sensitivity, searchability, and reporting eligibility, and review connected Audience, Lifecycle, Workflow, SLA, Permissions, Reporting, and Versions tabs.
Guided creation at `/w/:workspaceCode/settings/service-builder/guided` asks nontechnical authors for service ownership, audience, approval flow, required information, response and resolution targets, and reporting needs. It generates an independent service, form, draft version, section, typed field metadata, configuration snapshot, and audit event for continued editing in the existing Service Builder; it never publishes automatically.
AI-assisted design at `/w/:workspaceCode/settings/service-builder/ai-design` uses a provider-neutral `AiDesignProvider` interface to turn natural-language service descriptions into editable suggestions for sections, typed fields, rules, workflow, lifecycle, SLA, and reporting. The default local heuristics provider is replaceable by future hosted or self-managed models without changing Service Builder or metadata contracts. Suggestions create inactive draft metadata only, are audited as AI-assisted, and remain subject to administrator review, readiness checks, governance, and normal publication controls.
Publishing validates the complete draft, blocks broken or circular rule references, shows added, changed, removed, and renamed fields with rule, workflow, lifecycle, and reporting impacts, records an immutable configuration snapshot and audit event, and leaves every previous published version and historical request unchanged.
The shared `DynamicFormRenderer` is used for requester submission and builder preview, supports the full metadata field vocabulary, responsive layouts, immediate visibility/required/read-only rules, inline validation, and read-only/print modes. A shared Request Review Engine now derives human-readable section summaries, attachment overviews, validation warnings, and missing-information guidance from the same version-bound metadata and typed values. Requesters review and explicitly confirm before submission; the same summary is reused in the universal requester/technician view, approval handoff through that authorized view, and print exports. Lifecycle administration and the Automation Engine retain their existing entities. The visual Workflow Builder at `/w/:workspaceCode/settings/workflow-builder` extends those entities with a drag-and-drop canvas, zoom and pan, node properties, an accessible ordered representation, structural and field-reference validation, version binding, path preview, and a non-production test mode. Workflow snapshots are stored with the existing automation trigger configuration so execution remains configuration-derived without introducing a competing engine.
The Service Builder also includes a reusable component library for Address Block, Employee Selector, Manager Selector, Department Selector, Business Unit Selector, Cost Center Selector, Asset Selector, Date Range, Contact Block, Checklist, Editable Grid, Repeating Section, Approval Matrix, and Document List. Components are provider-neutral templates that expand into the existing versioned section, field, option, and configuration metadata; their answers continue through the same typed request-value pipeline and shared renderer, with no service-specific entities or rendering logic.

The governed Report Builder dynamically discovers non-sensitive reportable fields, scopes records before aggregation, and enables type-appropriate count, sum, average, minimum, and maximum operations for typed answers. Workspace administrators use the guided Migration Assistant at `/w/:workspaceCode/settings/migration-assistant` to analyze legacy forms, rules, workflows, SLAs, and reports; review stable-key mapping recommendations; generate an independent metadata draft; validate it; and run a non-production test that creates no requests or workflow state. Controlled cutover publishes the tested draft and switches only the existing catalog assignment for future submissions, while rollback restores the previous assignment. Migration plans and audit events retain ownership, warnings, target versions, cutover dates, and rollback state; historical requests and typed answers are never rewritten.

Request relationships use the existing shared `RequestRelationship` entity and universal request view to model Parent, Child, Related, Duplicate, Blocks, and Blocked By links without service-specific tables. Authorized technicians can link existing requests or create coordinated child requests, map typed answers by stable field key, and monitor rolled-up child completion and blockers. The visual workflow builder includes a configuration-driven Create Child Request node with target service, title, and stable-key mappings so orchestration can create cross-department work while preserving the parent request and workspace boundary.

The Business Rules Catalog at `/w/:workspaceCode/settings/business-rules` governs reusable Validation, Eligibility, Assignment, Approval, Workflow, and SLA definitions through stable rule keys and immutable published versions. Workspace administrators can author definitions, publish JSON condition and outcome snapshots, inspect dependencies and consumer usage, and review controlled service or form overrides. Existing FieldValidationRule, AssignmentRule, ApprovalRule, AutomationRule, and ServiceTargetRule records remain specialized execution adapters rather than competing rule engines.

Dependency mapping is embedded in the existing Service Builder rather than exposed as a competing administration surface. It traces fields, validation and conditional rules, reusable components, workflow snapshots, lifecycle and SLA configuration, reports, dashboards, and service templates through stable metadata references. Before publication, changes are classified as safe impacts, warnings, or breaking changes; mapped breaking dependencies block publication until corrected, while the complete dependency graph is retained in the immutable version snapshot for audit and historical review.

Service governance at `/w/:workspaceCode/settings/service-governance` assigns Service Owner, Service Designer, Workflow Designer, Report Author, Publisher, Auditor, and backup ownership independently for each service. Profiles define recurring review dates and maker/checker policy. When maker/checker is enabled, the Service Builder captures a mandatory change reason and creates a publication approval instead of publishing directly; only the assigned Publisher or platform administrator can approve it, and the maker cannot approve their own change. Approval or rejection records the reviewer, timestamp, comment, immutable version, and configuration audit event while preserving direct publication for existing services without a governance profile.
Service readiness is evaluated inside the existing Service Builder before publication. The assessment derives live results for Forms, Validation, Rules, Workflow, Lifecycle, SLA, Permissions, Reporting, and Dependencies from the selected draft and connected metadata. Each domain is classified as Ready, Ready With Warnings, or Not Ready, with exact remediation steps and direct links to the relevant builder tab. Not Ready findings block publication, while warnings remain visible for informed governance review; published versions and the requester marketplace at `/` are unchanged.
Email request intake is configured per workspace at `/w/:workspaceCode/settings/email-intake`. Administrators select a monitored mailbox folder, default service and catalog item, unknown-sender policy, and post-processing read behavior. Processing records use the immutable Microsoft message ID for deduplication, correlate replies by conversation ID, link origin and reply messages to the shared Request entity, and retain outcome and event history for retries, review, and audit. The scheduled mailbox processor remains an explicit production connector dependency; the application provides its configuration, persistence contract, and operational monitor.

## Design direction

The requester experience follows a premium, human-centered Rawabi service marketplace direction: deep corporate blue provides confidence and technical authority, teal supports service discovery, orange is reserved for purposeful actions, and generous whitespace keeps search dominant. The homepage uses an optional, compact Favorite Services collection and responsive discovery tabs, with touch-friendly service tiles and no exposed workspace or fulfillment terminology. Operational screens retain compact, structured layouts and explicit workspace context.

## Demo configuration and readiness

The in-memory edition intentionally retains explicit demo personas so administrators can test global, workspace, requester, agent, approver, auditor, and administrator boundaries without an external employee directory. The workspace administration screen provides a clear persona switcher, notification preferences, governance controls, and a launch readiness center.

The System Readiness Center consolidates the 50-action rollout into domain launch gates across access, catalog, requests, approvals, targets, contracts, automation, notifications, files, audit, deployment, and certification. Every gate identifies a capability state, named owner, blocker severity, and remediation route where the current app can resolve it. Persistent operational storage, enterprise identity, durable file handling, scheduled processors, and outbound delivery remain non-overridable future dependency blockers rather than simulated integrations.

Only entity-backed core modules are exposed in operational navigation: Home, Requests, Approvals, Reports, Contracts, and Knowledge. Problems and Changes remain retired, and specialist configurations without complete workflows stay hidden rather than routing users to placeholders.
